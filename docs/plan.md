# План backend

Схема того, из чего состоит backend и в каком порядке его делать. Требования —
в [spec.md](spec.md), экраны — в [screens.md](screens.md),
сценарии — в [use-cases.md](use-cases.md). План обновляется после каждого шага.

Обозначения: ✅ готово · ⏳ следующий шаг · ⬜ впереди.

## Карта

```
                       ┌──────────── Веб-приложение (React) ────────────┐
                       │      REST /api/*  +  WebSocket /api/ws         │
                       └───────────────────────┬────────────────────────┘
                                               │ cookie: access / refresh
┌──────────── Админка ───────────┐   ┌─────────▼──────────── src/api ──────────────────────┐
│ sqladmin  /admin  ✅ минимум    │   │ auth ✅ · profile ✅ · courses ✅ · materials ✅ · │
│ структура вуза, группы, почты, │   │ feed ✅ · announcements ✅ · assignments ✅ ·       │
│ преподаватели, студенты        │   │ submissions ✅ · reviews ✅ · schedule ✅ · home    │
└───────────────┬────────────────┘   │ calendar ✅ · personal_tasks ✅ · notifications ✅  │
                │                    └─────────┬───────────────────────────────────────────┘
                │                              │
┌───────────────▼──────────────────────────────▼──────── src/core ────────────────────────┐
│ security ✅ · access ✅ · s3 ✅ · grading ✅ · schedule ✅ · notifications ✅ ·         │

            PostgreSQL                    S3 / MinIO                  APScheduler (в процессе)
```

## Подсистемы `src/core`

| Подсистема | Что делает | Статус |
|---|---|---|
| `db` | модели всех сущностей, миграция, репозитории и UoW (дополняются по доменам) | ✅ модели, ⬜ репозитории по мере доменов |
| `security` | argon2, JWT, refresh-токены, текущий пользователь (`FromDishka[CurrentUser]`) | ✅ |
| `access` | проверки принадлежности: студент в группе курса, курс принадлежит преподавателю, группа прикреплена к преподавателю, курс не в архиве | ✅ |
| `s3` | клиент MinIO/S3: presigned-загрузка с лимитом 20 МБ, presigned-скачивание, удаление объектов | ✅ |
| `schedule` | чистая логика без I/O: сетка пар, семестры, правила и разовые занятия → занятия на период, номер и чётность недели, период календаря | ✅ |
| `notifications` | создание личных уведомлений в транзакции действия, слепок данных, заголовок и текст по типу, переход к объекту, напоминания о дедлайнах | ✅ |
| `realtime` | реестр WebSocket-соединений по пользователям и сессиям в памяти процесса; слушатель PostgreSQL (`LISTEN`) с переподключением | ✅ |
| `scheduler` | APScheduler: каждые 5 минут ищет дедлайны в ближайшие 24 часа и создаёт напоминания без дублей | ✅ |

## Админка (sqladmin, `/admin`, код в `src/admin`)

Готово (минимум, чтобы можно было работать):

- ✅ Вход только для роли `admin`: сессия — запись в `sessions`, как в веб-приложении.
- ✅ Админ создаётся командой `make create-admin` (спрашивает почту, ФИО и пароль); в запущенном `make up` стеке — `make create-admin-docker`.
- ✅ Подразделения, кафедры, направления — списки и редактирование; повтор названия или сокращения — понятная ошибка.
- ✅ Группы: создание с автоназванием (или ручным), код регистрации показывается один раз, перевыпуск кода. При правке нетронутое автоназвание пересобирается по новым полям, ручное остаётся.
- ✅ Почты группы: добавление по одной, перенос в другую группу, отметка «зарегистрирован».
- ✅ Преподаватели: создание со сгенерированным паролем (показывается один раз), прикрепление групп; неактивную группу прикрепить нельзя.
- ✅ Ошибки форм — в общем формате лога (`admin.error`: ожидаемые — info без стектрейса) и в `app_errors_total`; строки, которых нет в переводах sqladmin, — по-русски.

Позже, перед шагом 8:

- ⬜ Группы: создание пачкой, деактивация с вопросом про студентов, фильтры (подразделение, направление, уровень, форма, курс, активна).
- ⬜ Почты: вставка списком или CSV.
- ⬜ Преподаватели: деактивация с отзывом сессий.
- ⬜ Студенты: перевод в другую группу, деактивация, сброс пароля. Сброс и деактивация отзывают все сессии.

## Порядок работы

1. ✅ **Фундамент.** Модели, первая миграция, auth, тесты (unit + integration).
2. ✅ **Админка, минимум.** Без структуры вуза, групп, почт и преподавателей приложением не воспользоваться. Плюс `make create-admin`.
3. ✅ **Курсы и доступ.** `courses` и `core/access` — от них зависят все остальные домены.
   Готово: UC-T2, UC-T3, UC-T4, UC-T15, UC-S2 (шапка курса). Эндпоинты `/api/courses`: список плиток (и архив) с пагинацией, полная карточка курса, создание (минимум одна группа), изменение, добавить/убрать группу (курс без групп остаётся у преподавателя), архив/возврат, группы для выбора (поиск по части названия, фильтры по уровню, форме и году набора, пагинация).
   Уведомление «вас добавили в курс» сделано на шаге 7. Счётчики «ждут проверки» на плитках, материалы и лента курса сделаны на шагах 4–5.
4. ✅ **Файлы.** `core/s3` и MinIO в docker-compose; материалы курса, профиль и аватарки.
   Готово: UC-T5 (материалы), UC-C5 (аватарка), профиль. Материал — пост: название, текст в markdown (ссылки — в тексте) и сколько угодно файлов; файлы — отдельная таблица `course_material_files`. Загрузка — напрямую из браузера в S3:
   `POST …/uploads` → форма presigned POST (лимит 20 МБ проверяет и S3) → браузер грузит файл → `POST` с ключом, бэкенд берёт размер и тип из S3.
   Эндпоинты: `/api/courses/{id}/materials` (список с пагинацией и ссылками на скачивание, создание, правка, `…/{material_id}/files` — прикрепить и убрать файл, удаление материала со всеми файлами одним запросом к S3), `/api/profile` (профиль, загрузка, замена и удаление аватарки; аватарка — только PNG, JPEG, WebP, GIF).
   Локальный S3 — образ `pgsty/minio` (сборка MinIO): официальные образы MinIO больше не публикуются. Бакет и учётку бэкенда (доступ только к объектам бакета) создаёт `minio-init` скриптом `deploy/minio/init.sh`; root MinIO — только для консоли.
   Файлы заданий и попыток сделаны на шаге 5, уведомление «новый материал» — на шаге 7.
5. ✅ **Задания, сдачи, проверка.** `core/grading`, `feed`, `announcements`, `assignments`, `submissions`, `reviews`.
   Готово: UC-T6–T13, UC-S2 (лента), UC-S3–S6. Объявления и общая лента курса вошли в этот шаг.
   Эндпоинты:
   - `GET /api/courses/{id}/feed?type=&page=&per_page=` — лента;
   - `/api/courses/{id}/announcements[/{announcement_id}]` — объявления;
   - `/api/courses/{id}/assignments` — `uploads`, создание, `/{assignment_id}` (карточка, правка, удаление), `…/files[/{file_id}]`, `…/students?group_id=&status=&page=&per_page=` — таблица студентов постранично;
   - `/api/courses/{id}/assignments/{assignment_id}/submissions` — `uploads`, отправка, моя история;
   - `…/students/{student_id}/submissions` — экран проверки;
   - `…/submissions/{submission_id}/review` — `POST` проверить, `PUT` исправить оценку и комментарий;
   - `GET /api/reviews/queue?course_id=&assignment_id=` — очередь;
   - плитка курса преподавателя — `pending_reviews`.
   Принятые решения: новая попытка разрешена, пока прежняя на проверке, проверяется только последняя; при исправлении вердикт не меняется; шкалу курса нельзя менять, если по заданию со шкалой курса есть попытки; «просрочено» — только при мягком дедлайне. Статус и текущая оценка считаются из попыток (`core/grading`), а не хранятся.
   Уведомления («новое задание», «задание изменено», «новое объявление», «работа проверена», «оценка изменена», «новая попытка») сделаны на шаге 7.
6. ✅ **Расписание и календарь.** `core/schedule`, `schedule`, `calendar`, `personal_tasks`.
   Готово: UC-T14, UC-C8, UC-S7. Курс привязан к семестру (`term` + `year`, задаются при создании и дальше не меняются; без выбора — текущий по дате). Осенний (нечётный) — с 1 сентября по 31 января, пары до 30 декабря включительно; весенний (чётный) — с 1 февраля по 10 июля. Границы и сетка пар — в `[schedule]` конфига.
   Занятия ставятся только в окнах пар: 1) 09:30–11:00, 2) 11:15–12:45, 3) 13:00–14:30, 4) 15:10–16:40, 5) 16:55–18:25. В запросе — номер пары `slot`, время берёт бэк; личные задачи со временем не связаны.
   Эндпоинты:
   - `GET /api/schedule/slots` — сетка пар;
   - `GET /api/courses/{id}/schedule` — семестр, правила и разовые занятия (студенту — своей группы);
   - `POST/PUT/DELETE /api/courses/{id}/schedule/rules[/{rule_id}]` — правила с повтором `weekly/even/odd`;
   - `POST/PUT/DELETE /api/courses/{id}/schedule/extras[/{extra_id}]` — разовые занятия («допы») на дату внутри семестра, пока идут пары;
   - `GET /api/calendar?view=day|week|month&date=` — период (`starts_on`, `ends_on`, `prev`, `next`), недели с номером и чётностью, события; месяц — целыми неделями;
   - `/api/personal-tasks` — `GET ?from=&to=`, `POST`, `PUT /{id}`, `PATCH /{id}/done`, `DELETE /{id}`.
   Принятые решения: номер недели считается от начала семестра (неделя 1 — пн–вс с датой начала, нечётная), летом номера нет; пересечения занятий по времени не запрещаются (возможны подгруппы); архивные курсы и задания без дедлайна в календаре не показываются; у дедлайна студент видит свой статус сдачи.
   Уведомление «расписание изменено» сделано на шаге 7.
6б. ✅ **Экзамены и итоговые оценки.** `exams`, `final_grades`. Готово: UC-T16, UC-T17, UC-S8.
   У группы в курсе один итоговый контроль: зачёт (`credit`), дифф. зачёт (`graded_credit`) или экзамен (`exam`), с датой, парой из сетки и аудиторией. Дата — в пределах семестра курса, в том числе в сессию после 30 декабря (осенью — до 31 января).
   Итоговый результат студента зависит от формы контроля его группы: зачёт — `passed` (зачтено или нет), дифф. зачёт и экзамен — `grade` 2–5 (2 — не сдал, 3 — удовлетворительно, 4 — хорошо, 5 — отлично). Его ставит и исправляет преподаватель, студент видит свой. Если группе не назначена форма контроля — 422; результат не того вида — 422. Пока по экзамену есть результаты, его нельзя удалить или сменить форму и группу (409).
   Эндпоинты:
   - `GET/POST /api/courses/{id}/exams`, `PUT/DELETE …/exams/{exam_id}` — экзамены (студенту в `GET` — своей группы);
   - `GET /api/courses/{id}/final-grades?group_id=&page=&per_page=` — таблица курса с оценками (`grade: null` — не выставлена);
   - `PUT/DELETE /api/courses/{id}/final-grades/{student_id}` — выставить, исправить или снять результат (`{"passed": true}` для зачёта, `{"grade": 4}` для остальных);
   - `GET /api/courses/{id}/final-grades/me` — своя оценка студента;
   - в календаре экзамены идут событиями вида `exam`.
   Принятые решения: студент должен быть активным и состоять в группе курса; в архивном курсе результаты и экзамены менять нельзя.
   Уведомление «итоговый результат выставлен» сделано на шаге 7.
7. ✅ **Уведомления.** `core/notifications`, `core/realtime`, `core/scheduler`, `notifications`, WebSocket, напоминания через APScheduler.
   Готово: UC-C6, UC-C7, UC-SYS1.
   Уведомления личные, по строке на получателя. Создаются в той же транзакции, что и действие (`NotificationService`), поэтому откат действия откатывает и их. В БД лежит слепок данных (`data`); заголовок, текст и переход собираются при чтении по типу (`NotificationRenderer`), так что формулировки правятся без миграции.
   В ответе: `id`, `type`, `title`, `text`, `course` (id и название), `target` (`section` и идентификаторы для быстрого перехода: `assignment`, `course_feed`, `materials`, `schedule`, `calendar`, `review`, `final_result`; `course_id`, `assignment_id`, `submission_id`, `student_id`, `day`), `is_read`, `created_at`.
   События: студентам — курс добавил их группу, новое задание, материал и объявление, задание изменено, расписание изменено, назначен или изменён зачёт или экзамен, работа проверена, оценка исправлена, выставлен итоговый результат, напоминание о дедлайне; преподавателю — новая попытка. Для «изменено» (задание, расписание, экзамен, оценка) пока старое уведомление не прочитано, новое не создаётся, а прежнее обновляется свежими данными и временем; это решает сама БД (`ON CONFLICT`), без лишних запросов.
   Эндпоинты:
   - `GET /api/notifications?unread=&page=&per_page=` — список, новые первыми;
   - `GET /api/notifications/unread-count`;
   - `POST /api/notifications/{id}/read` и `POST /api/notifications/read-all`;
   - `GET /api/ws` (WebSocket) — `ready` с числом непрочитанных, затем `notification` (само уведомление и `unread_count`), `ping` раз в 30 секунд и `resync`.
   Доставка: триггер БД на `notifications` шлёт `NOTIFY` (тоже только после коммита), слушатель PostgreSQL получает событие, находит соединения адресата в реестре и пишет в них. Одно подключение слушателя на процесс; при обрыве оно переподключается, а клиенты получают `resync` и перечитывают список. Недоставленное лежит в БД и видно в списке.
   WebSocket: аутентификация по access-cookie при подключении; закрытие `4401` — нет входа или сессия отозвана, `4403` — запрос с чужого сайта (проверка `Origin` по `cors.origins`). Отзыв сессии (выход, смена пароля, блокировка) ловит триггер на `sessions` и закрывает её соединения.
   Напоминания: APScheduler в процессе приложения, раз в 5 минут и сразу при старте; заданию с жёстким или мягким дедлайном в ближайшие 24 часа в неархивном курсе, студентам без единой попытки; одно напоминание на студента и задание (уникальный индекс), даже если дедлайн потом сдвинули.
8. ⬜ **Главная и финиш.** Остаток админки (см. выше), `home`, README, скриншоты, проверка требований раздела 16 спеки.

Каждый шаг: модели и репозитории (если нужны) → сервисы → роутеры → тесты сценариев в `tests/scenarios.toml` → `make check` и `make test-all`.

## Сквозные решения

- **Время:** моменты в UTC (`timestamptz`), настенное время расписания и личных задач — по МСК; ввод и вывод дедлайнов по МСК.
- **Файлы:** только через presigned URL. Лимит 20 МБ задаётся в presigned POST-политике: presigned PUT размер не ограничивает.
- **Доступ:** любая выборка по курсу проходит через `core/access`; курса нет → 404, чужой курс → 403, курс в архиве → 409. Ошибки `core/access` каждый домен переводит в свои (`raise ... from exc`), так цепочка причин видна в логах.
- **Пагинация:** растущие списки и списки для выбора отдаются постранично: `?page=&per_page=` → `{items, page, per_page, total, pages}`. `per_page` по умолчанию 20, максимум 100 (`[pagination]` в конфиге); страница за последней — пустая, пустой список — одна пустая страница. Порядок задаёт домен (курсы — новые первыми, группы — по алфавиту) и всегда однозначен.
- **Список и карточка:** в списке — лёгкая плитка, полные данные — в отдельном запросе карточки.
- **Загрузка файлов:** фронт держит выбранные файлы в состоянии формы и загружает их в S3 только по кнопке отправки, затем одним запросом создаёт запись (спека, §13). Так файл, от которого отказались, в бакет не попадает.
- **Изменение записи с файлами:** прикрепление и удаление файла двигает `updated_at` записи, как и правка текста.
- **Ключи файлов в S3:** у каждого вида — свой префикс: `courses/{id}/materials/`, `courses/{id}/assignment-files/`, `courses/{id}/submissions/{assignment_id}/{student_id}/`, `users/{id}/avatar/`. Ключ проверяется по префиксу, поэтому чужой файл к записи не прикрепить.
- **Дедлайны:** ввод — время с часовым поясом, без пояса считается МСК; в ответах `deadline_at` — по МСК (`+03:00`). Прочие моменты — в UTC.
- **Гонки на уникальных связях:** проверка «уже есть» в сервисе дополняется переводом нарушения уникальности при commit в ту же доменную ошибку (например, повторное добавление группы в курс — 409, а не 500).
- **Файл и запись удаляются вместе:** запись удаляется в транзакции, затем файл в S3, затем commit; S3 не ответил — 503, всё остаётся как было.
- **Архив:** архивный курс только для чтения; проверка в `core/access`.
- **Пароль:** от 8 до 32 символов везде — регистрация, вход, смена пароля, вход в админку, `make create-admin`.
- **Обязательные настройки** перечислены в `Config.missing_required()`; без них приложение не стартует и пишет в лог, каких нет.
- **Образы Docker** — с точной версией, без `latest` (compose, Dockerfile, тестовые контейнеры).
- **MinIO:** бэкенд работает под своей учёткой (`S3_ACCESS_KEY`/`S3_SECRET_KEY` в `.env`) с правами только на объекты своего бакета; root MinIO — для консоли.
- **Один процесс:** APScheduler и реестр WebSocket живут в памяти, поэтому uvicorn работает с одним воркером. Приложение асинхронное, на вуз этого хватает с запасом.
- **Если понадобится несколько воркеров:** APScheduler вынести в отдельный процесс (иначе работа напоминаний задвоится: повторов не будет, их отсекает БД). Доставка уведомлений и закрытие соединений уже построены на `LISTEN/NOTIFY`: каждый воркер получает события и пишет только в свои соединения, новая инфраструктура не нужна.
- **Статусы и сводки считает БД.** Положение студента по заданию (`core/db/repositories/submission.py`, `_progress`) — один запрос с группировкой по паре «задание + студент»: статус, число попыток, последняя попытка и последняя выставленная оценка. Таблица студентов по заданию и сводки в ленте и карточке берутся оттуда; фильтры по группе и статусу и пагинация — в SQL, фронт ничего не считает. Статус по-прежнему нигде не хранится.
- **Отказ не оставляет файлов в S3.** Если запрос с ключами файлов отклонён (архив, неверный ключ, повтор, сбой), бэкенд сам удаляет из S3 присланные файлы (`S3Storage.discard_on_error`). Удаляются только ключи со своим префиксом, не прикреплённые ни к какой записи: чужой или уже используемый файл так не стереть. Если сама очистка не удалась, в лог пишется `s3.discard_failed`, а клиент получает исходную ошибку.

## Известные хвосты

- README всё ещё от шаблона — переписать на шаге 8.
- Мусор в S3 после загрузки: если запрос «добавить» до бэка не дошёл (закрыта вкладка, пропала сеть), загруженный файл остаётся в бакете. Отказ бэка закрыт: см. «Сквозные решения».
- Удаление материала, файла материала или аватарки: если файл в S3 удалился, а коммит в БД упал, запись ссылается на удалённый файл. Возможно только при отказе БД в этот момент — принятая цена.
- Безопасность загрузки в рамках MVP не усиливается: содержимое файлов не проверяется, тип не ограничивается (у аватарки — только PNG, JPEG, WebP, GIF).
- WebSocket проверяет токен только при подключении: если access-токен истёк, а сессия жива, соединение остаётся открытым до отзыва сессии или обрыва связи. Истечение самой сессии (30 дней) соединение не закрывает.
- Уведомления не удаляются автоматически, чистка старых — позже.
- Напоминание не повторяется, если после него сдвинули дедлайн.
- Две вкладки, одновременный refresh: сессия отзывается как при краже — принятая цена.
- Ничего не закоммичено: весь backend — в рабочей копии. Требование курса — регулярные осмысленные коммиты (спека, §16).
- Курсы: студенты деактивированной группы продолжают видеть её курсы — так решили по умолчанию, в спеке не описано.
- Вход в API и админку не ограничивает число попыток. При неизвестной почте пароль не проверяется, поэтому ответ быстрее — по времени можно понять, есть ли почта. Решение отложено.
- Отсутствие объекта проверяется по 404 от S3. MinIO отдаёт 404 и учётке без `s3:ListBucket`; настоящий AWS S3 в этом случае отдаёт 403 — при переезде на AWS политике бэкенда понадобится `s3:ListBucket`.
- Загрузка из браузера напрямую в MinIO (CORS с `localhost:3000`) из настоящего браузера не проверялась — только запросами без браузера.
- Контейнер `migrate` пишет предупреждение pydantic-settings: `config.toml` в него не монтируется, хотя `toml_file` задан. На работу не влияет.
- Студент, которого перевели в другую группу или чью группу убрали из курса, пропадает из очереди и таблицы, но его попытки остаются; проверить их можно по прямой ссылке на экран проверки.

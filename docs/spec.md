# Labka — спецификация

Трекер лабораторных работ и домашних заданий: курсы с лентами заданий и материалов, управление доступом, расписание, планер, уведомления.

Связанные документы:
- [Экраны](screens.md) — что находится на каждом экране и куда с него можно перейти.
- [Юзкейсы](use-cases.md) — сценарии по ролям.
- [План backend](plan.md) — что уже сделано и что дальше.

## 1. Стек

- Backend: Python + FastAPI.
- БД и ORM: PostgreSQL + SQLAlchemy (async), миграции — Alembic.
- Frontend: React + TypeScript, готовая библиотека UI-компонентов, упрощённый Feature-Sliced Design, базовая адаптивность.
- Админка: `sqladmin`.
- Файлы: S3 (локально MinIO).
- Фоновые задачи: APScheduler.

## 2. Роли

| Роль | Как работает | Что может |
|---|---|---|
| **Админ** | Админка (`sqladmin`) | Ведёт структуру вуза (подразделения, кафедры, направления, группы), списки почт групп и коды регистрации, создаёт преподавателей, переводит студентов между группами, прикрепляет группы к преподавателям, сбрасывает пароли, деактивирует пользователей и группы |
| **Преподаватель** | Веб-приложение | Создаёт курсы, добавляет в них свои группы, публикует задания, материалы и объявления, задаёт шкалы, проверяет сдачи, составляет расписание |
| **Студент** | Веб-приложение | Регистрируется по коду группы, видит курсы своей группы, сдаёт работы, смотрит оценки и расписание, ведёт личные задачи в календаре |

- Студент состоит ровно в одной группе.
- У курса ровно один преподаватель.

## 3. Структура вуза

Структура повторяет устройство МТУСИ в упрощённом виде:

```
Подразделение (факультет / центр)
 ├── Кафедра ───────── преподаватели
 └── Направление ───── группы ───── студенты
```

- **Подразделение** — факультет (например, «Информационные технологии») или центр (например, «Центр заочного обучения по программам бакалавриата»).
- **Кафедра** принадлежит подразделению. У преподавателя указывается кафедра — только для информации, на права не влияет.
- **Направление** — сокращение (`ВТ`, `ПИ`, `СТ`…), название, подразделение.
- **Группа** — направление, уровень (`Б` бакалавриат / `С` специалитет / `М` магистратура), форма обучения (очная / очно-заочная / заочная), год набора, номер, название.
  - Название собирается автоматически: уровень + направление + две последние цифры года набора + номер (`Б` + `ВТ` + `26` + `01` = `БВТ2601`). Его можно исправить вручную (для нестандартных названий вроде `М092401(71)`).
  - Курс (1, 2, 3…) не хранится, а вычисляется из года набора: 1 сентября все группы переходят на следующий курс.
  - Группы можно создавать пачкой: направление, год, уровень, форма и количество → `БВТ2601…БВТ2604`.

## 4. Регистрация и вход

### 4.1. Студенты — по коду группы

1. Админ добавляет в группу список почт студентов (по одной на строку или из CSV).
2. У группы есть код регистрации; админ передаёт его группе (например, старосте).
3. Студент открывает страницу регистрации, вводит почту, код группы, ФИО и пароль.
4. Регистрация проходит, только если код верный и почта есть в списке этой группы и ещё не использована. Студент попадает в эту группу.

- Код группы можно перевыпустить — старый перестаёт действовать.
- Почту можно убрать из списка или перенести в другой; уже зарегистрированных студентов это не затрагивает.
- В списке почт админ видит, кто уже зарегистрировался.

### 4.2. Преподаватели — создаёт админ

- Админ вводит ФИО, email и кафедру. Пароль генерируется автоматически и сразу после сохранения показывается на экране (с кнопкой «скопировать»). Позже его посмотреть нельзя.

### 4.3. Пароли

- Пароли хранятся как стойкие хэши, предназначенные для паролей (argon2 или bcrypt).
- Длина пароля — от 8 до 32 символов, везде, где пароль задаётся или вводится.
- Пользователь меняет пароль сам в профиле.
- Забытый пароль: админ генерирует новый — он показывается один раз.
- Вход по email и паролю. Email уникален.
- В админку пускаются только пользователи с ролью `admin`.

### 4.4. Сессии и токены

- Каждый вход создаёт запись в таблице сессий (`Session`) — это список разрешённых сессий.
- Access-токен — JWT на 15 минут, содержит `session_id`. На каждом запросе (и при подключении WebSocket) проверяется, что сессия существует и не отозвана.
- Refresh-токен — случайная строка; в БД хранится её хэш. При обновлении выдаётся новый refresh-токен, старый перестаёт действовать (ротация).
- Повторное использование уже заменённого refresh-токена считается кражей: сессия отзывается.
- Logout отзывает текущую сессию — украденные access- и refresh-токены этой сессии сразу перестают работать, WebSocket закрывается.
- Смена пароля отзывает все остальные сессии пользователя: в той, где пароль сменили, он остаётся в системе. Сброс пароля админом отзывает все сессии.

## 5. Управление доступом

Доступ определяется ролью (RBAC) и проверкой принадлежности:

- Студент видит курс, только если в курс добавлена его группа.
- Студент видит только свои сдачи и свои личные задачи.
- Преподаватель видит только свои курсы и сдачи по ним.
- Преподаватель может добавить в курс только группы, прикреплённые к нему админом.
- Деактивированный пользователь не может войти; его сессии отзываются.
- Админские операции доступны только через админку.

## 6. Работа админа с группами и пользователями

- **Перевод студентов**: выбрать одного или нескольких студентов → указать новую группу. Студент видит курсы новой группы, старые попытки остаются в БД.
- **Деактивация пользователя** вместо удаления: войти нельзя, данные остаются. Можно активировать обратно.
- **Деактивация группы** вместо удаления. Админ получает вопрос «Деактивировать студентов группы?»; при согласии деактивируются и они. Неактивную группу нельзя добавить в курс, по её коду нельзя зарегистрироваться.
- **Открепление группы от преподавателя**: в уже созданных курсах группа остаётся, в новые её добавить нельзя.
- Фильтры групп: подразделение, направление, уровень, форма, курс, активна.

## 7. Курсы

- У преподавателя может быть сколько угодно курсов.
- Курс может быть для одной группы или для нескольких.
- У курса есть шкала оценки по умолчанию и пояснение, как составляется оценка (см. 8.1).
- У курса есть общие **материалы** — то, что относится ко всему курсу (учебник, методичка по оформлению, полезные ссылки и т. п.). Материал — название, текст в markdown (ссылки — прямо в тексте) и сколько угодно файлов; текст и файлы необязательны.
- Преподаватель меняет название и текст материала, прикрепляет к нему новые файлы, убирает файлы и удаляет материал целиком (вместе с файлами).
- В ленте курса публикуются **задания** и **объявления** (текстовые посты в markdown, например «пара переносится»). Преподаватель может редактировать и удалять объявления.
- Курс можно отправить в **архив** (например, после окончания семестра) и вернуть из архива. Архивный курс доступен только для чтения: нельзя сдавать работы и что-либо менять. Он пропадает из основного списка, напоминания по нему не приходят.
- Группу убрали из курса → курс пропадает у её студентов, их попытки остаются в БД.

## 8. Задания

- Тип задания: `lab` (лабораторная), `practice` (практическая), `hw` (домашнее задание). Название задаётся произвольно.
- Черновиков нет: задание видно студентам сразу после создания.
- Описание в markdown; преподаватель может прикрепить к заданию файлы (указания, методичка).
- Если по заданию уже есть попытки, можно менять текст, файлы и дедлайн, но нельзя менять шкалу. Удалить задание можно — вместе со всеми попытками.

### 8.1. Шкала оценки

- Тип шкалы:
  - `range` — оценка в диапазоне `min..max` (например, 2–5 или 0–10);
  - `binary` — зачёт / незачёт.
- Курс задаёт шкалу по умолчанию; задание может её переопределить.
- И у курса, и у задания есть текстовое поле с пояснением, как составляется оценка.
- Итоговой оценки за курс нет — только оценки по каждой работе.

### 8.2. Дедлайны

Преподаватель выбирает тип дедлайна для каждого задания:

| Тип | Поведение |
|---|---|
| `none` | Дедлайна нет, сдавать можно когда угодно |
| `soft` | После дедлайна сдать можно, попытка помечается как просроченная |
| `hard` | После дедлайна первую попытку отправить нельзя. Если хотя бы одна попытка отправлена до дедлайна, пересдачи после возврата на доработку разрешены и позже |

## 9. Сдача и проверка

- Сдача только индивидуальная.
- Попытка содержит файлы (несколько) и комментарий; оба поля необязательны, но пустую попытку отправить нельзя.
- Все попытки хранятся (история). Студент не может удалить или отредактировать отправленную попытку — только отправить новую.
- После вердикта «принято» новые попытки по заданию отправить нельзя.
- Преподаватель на попытку ставит вердикт, оценку и комментарий (markdown):
  - `revision` — на доработку; оценка необязательна (например, «сейчас 4, доделай — будет 5»);
  - `accepted` — принято; оценка обязательна.
- Текущая оценка студента за задание — оценка из последней проверенной попытки, где она выставлена.
- Преподаватель может исправить уже поставленную оценку.

Статус задания для студента:

```
не сдано → на проверке → на доработку (возможно, с оценкой) → на проверке → … → принято (с оценкой)
```

## 10. Расписание

- Расписание не хранится как сетка — оно вычисляется из правил, которые задаёт преподаватель (в настройках курса).
- Правило: курс, группа, тип занятия (`lab` / `practice`), день недели, время начала и конца, повтор (`weekly` / `even` / `odd`), аудитория (необязательно).
- Лекций нет.
- Студент видит правила для своей группы, преподаватель — свои.
- Чётность недели считается от начала семестра:
  - с 1 февраля по 31 августа — от 1 февраля;
  - с 1 сентября по 31 января — от 1 сентября.
- Неделя 1 — календарная неделя (пн–вс), в которую попадает дата начала семестра; она нечётная, дальше недели чередуются.

## 11. Календарь (планер)

Планер и расписание объединены в один календарь (неделя / месяц). В нём показываются:

- занятия (из правил расписания);
- дедлайны заданий;
- **личные задачи** студента: название, дата, время (необязательно), отметка «сделано». Видит только сам студент; создаются, отмечаются, изменяются и удаляются прямо в календаре.

У преподавателя аналог планера — **очередь на проверку**: все непроверенные попытки по его курсам.

## 12. Уведомления

- Доставка — push через WebSocket. Уведомления хранятся в БД, чтобы оффлайн-пользователь увидел их при следующем входе.
- События для студента:
  - его группу добавили в курс;
  - новое задание, материал или объявление в курсе;
  - изменено задание (текст, дедлайн, файлы);
  - изменено расписание его группы;
  - работа проверена или оценка исправлена;
  - напоминание за 24 часа до дедлайна, если работа ещё не сдана.
- События для преподавателя:
  - пришла новая попытка.

## 13. Файлы

- Все файлы (материалы курса, файлы заданий, файлы попыток, аватарки) хранятся **только в S3**. Локально — MinIO.
- В БД хранятся только ключи объектов и метаданные (имя, размер, тип).
- Файлы не проходят через бэкенд: бэкенд выдаёт presigned URL, браузер загружает и скачивает напрямую из S3.
- Лимит 20 МБ на файл, тип не ограничивается. Исключение — аватарка: только PNG, JPEG, WebP или GIF (SVG нельзя: в нём может быть скрипт).
- Порядок загрузки (материал, задание, попытка, аватарка):
  1. Пользователь выбирает файлы — фронт держит их у себя в состоянии формы и **никуда не загружает**.
  2. По кнопке «Добавить» / «Сохранить» / «Отправить» фронт для каждого файла просит у бэкенда форму загрузки (`…/uploads`) и загружает файл напрямую в S3, показывая прогресс.
  3. Затем фронт одним запросом отправляет бэкенду запись с ключами загруженных файлов.
  - Файл, который выбрали и убрали или форму с которым закрыли, в S3 не попадает.
  - Удалить файл из S3 фронт не может и не должен: права на удаление у браузера нет. Убирать файлы, которые не стали частью записи, — забота бэкенда и хранилища.

## 14. Время и фоновые задачи

- Часовой пояс — **Москва** (`Europe/Moscow`). В БД время хранится в UTC; дедлайны и время занятий вводятся и показываются по МСК.
- Фоновые задачи — **APScheduler** внутри приложения:
  - каждые 5 минут ищет задания с дедлайном в ближайшие 24 часа и студентов, которые ещё ничего не сдали, и шлёт им напоминание;
  - повторно напоминание не шлётся: перед отправкой проверяется, нет ли уже такого уведомления для пары «студент + задание» (поэтому перенос дедлайна, перезапуск приложения и т. п. ничего не ломают).
- Предполагается один экземпляр бэкенда. Если их станет несколько, задачам понадобится блокировка, чтобы они не выполнялись дважды.

## 15. Модель данных (черновик)

| Сущность | Поля |
|---|---|
| `Faculty` | название, сокращение, тип (`faculty` / `center`) |
| `Department` | `faculty_id`, название |
| `Direction` | `faculty_id`, сокращение (`ВТ`), название |
| `Group` | `direction_id`, уровень (`Б` / `С` / `М`), форма обучения, год набора, номер, название, код регистрации (хэш), активна |
| `GroupInvite` | `group_id`, email, `user_id` (заполняется после регистрации) |
| `User` | ФИО, email (уникальный), пароль (хэш), роль (`admin` / `teacher` / `student`), `group_id` (только у студента), `department_id` (только у преподавателя), аватарка (ключ в S3), активен |
| `Session` | `user_id`, хэш refresh-токена, создана, истекает, отозвана, user-agent |
| `TeacherGroup` | `teacher_id`, `group_id` |
| `Course` | `teacher_id`, название, описание, тип шкалы, `min`, `max`, пояснение к оценке, архивирован |
| `CourseGroup` | `course_id`, `group_id` |
| `CourseMaterial` | `course_id`, название, текст (markdown), дата |
| `CourseMaterialFile` | `material_id`, файл |
| `Announcement` | `course_id`, текст (markdown), дата |
| `Assignment` | `course_id`, тип (`lab` / `practice` / `hw`), название, описание, тип дедлайна, дата дедлайна, шкала (необязательно, переопределение), пояснение к оценке |
| `AssignmentFile` | `assignment_id`, файл |
| `Submission` | `assignment_id`, `student_id`, номер попытки, комментарий, флаг «просрочено», дата |
| `SubmissionFile` | `submission_id`, файл |
| `Review` | `submission_id`, вердикт (`accepted` / `revision`), оценка (число или зачёт/незачёт; обязательна при `accepted`, необязательна при `revision`), комментарий |
| `ScheduleRule` | `course_id`, `group_id`, тип занятия, день недели, время начала и конца, повтор, аудитория |
| `PersonalTask` | `student_id`, название, дата, время, сделано |
| `Notification` | `user_id`, тип события, данные, прочитано |

Файл — ключ объекта в S3, имя, размер, MIME-тип.

## 16. Требования курса к сдаче

Из методички «Fullstack, первый семестр»:

- Регулярные коммиты с осмысленными сообщениями; одна загрузка готового проекта в конце не засчитывается.
- README: описание проекта, экраны и сценарии, модель данных, зависимости, настройка окружения, запуск frontend, backend и БД.
- `.gitignore`; секреты в репозиторий не попадают, пример конфигурации — без секретов.
- Скриншоты экранов — в `docs/screenshots`, обновляются при изменениях интерфейса.
- Понятные сообщения об ошибках и подходящие HTTP-статусы.
- На фронте: клиентская валидация форм, состояния загрузки / ошибки / отсутствия данных, осмысленные анимации переходов.
